# gpu13 Qwen3.8 move to GPU 2

> **Deployment blocker:** `origin/main` already includes PR #338, which changes gpu13 GLM from the live `model-sg-glm53-fp8-tp4` to `model-sg-glm53-w4afp8-tp2-r1a` and `-r1b`. That GLM change was not deployed when this plan was written (2026-10-06). Compose Manager runs `up -d --remove-orphans` for the whole project even when `services` is scoped. Any gpu13 `compose/up` from a tag containing #338 will therefore remove the live GLM TP4 container. **Do not deploy Stage A until Henry's gpu13 stage 1b has been deployed, or schedule both in the same jointly approved window.** Refresh the live tag, GLM container identities, and approval before either path.

## Why and capacity cost

The privacy filter and Qwen3.8 r1 share gpu13 GPU 0. Qwen3.8's 0.60 static pool did not cap allocations outside the pool: its observed footprint rose from about 88 GiB to about 122 GiB by 2026-10-05. That left under 18 GiB of free VRAM for privacy-filter batches that can need about 22 GB. The filter entered an OOM-like crash loop. The exact Docker exit code and first failing request were not captured, so confirm runtime health during the move rather than treating a green proxy health check as proof.

Qwen3.8 will take GPU 2, currently held by Qwen3.6 r2, using the qualified gpu02 dedicated recipe (`--mem-fraction-static 0.85`, `--max-mamba-cache-size 320`). Qwen3.6 r1 remains on GPU 1, so Qwen3.6 loses replica redundancy and can queue during its known peaks: one replica's effective running limit is about 70, while combined demand exceeded 70 for 222 minutes in the prior seven days. Watch its queue, TTFT, errors, and remaining r1 health throughout the rollout. This is a capacity trade-off, not spare capacity.

| B, separate branch and tag | Qwen3.8 r1 absent; Qwen3.8 proxy uses r2 only; GPU 0 reserved for privacy-filter | GPU 0 free VRAM approximately 138 GiB minus the filter; Qwen3.8 route healthy |

Use a low-traffic window. Treat each stage as its own approval and release. Stage A does **not** isolate the filter yet; its GPU 0 Qwen replica remains until Stage B. Independently approve the later privacy-filter recreate for PR #223.

## Common preflight for each stage

1. Confirm the blocker above is cleared. Record the actual Compose Manager instance, current tag and source file, registry endpoints, model-proxy synthetics, `docker/ps`, GPU 0/1/2 free VRAM, and Qwen3.6/Qwen3.8 error, queue, and TTFT baselines. Capture **every** container ID and `CreatedAt` before the first operation; compare after every call and stop if a non-target identity changes.
2. GET the gpu13 dashboard environment map and retain the **complete** map, including any keys not listed in this file. Send that full map as the `env` object on every Compose Manager call; `env_vars` in a request is ignored. Re-read and compare the map after the stage. Never replace it with a partial Qwen-only map or print credential values in rollout evidence.
3. Use the pinned, approved release tag and `file: prod/small-models.yaml` for every call. Supply a nonempty explicit `services` list. For each `compose/up`, first call the same operation with `dry_run: true`; inspect all creates, recreates, removals, and dependency actions. Apply with `dry_run: false` only when the plan has no unapproved changes. Use `force_recreate: false` except the named nginx calls below. A `compose/down` dry run is **not** a preview: Compose Manager ignores `dry_run` on down.
4. Be ready to verify each route with a real authenticated model request, the model-proxy registry, and its synthetic. `/v1/models` or a 200 alone is insufficient. Preserve before/after container ID and `CreatedAt` snapshots and monitor 5xx, restarts, GPU VRAM, Qwen3.6 queue/TTFT, and Qwen3.8 completions.

## Stage A: establish the GPU 2 replica

1. On the **current deployed tag**, call `compose/down` with `services: ["model-sg-qwen36-35b-a3b-fp8-tp1-r2"]`. Do not send a dry-run down. Wait for the container to exit and GPU 2 memory to clear. Qwen3.6 r1 on GPU 1 must stay healthy. The deployed inference-proxy build `0f37728` health-checks every backend in `VLLM_BACKEND_URLS` every 5 s with a 3 s timeout and marks it unhealthy after 3 consecutive failures. While the old Qwen3.6 proxy still lists r2, requests routed to the downed r2 can error for at most about 15 s before the proxy skips it; r1 then serves alone until step 3.
2. On the **Stage A tag**, dry-run then apply `compose/up` with `services: ["model-sg-qwen38-27b-fp8-tp1-r2", "dcgm-qwen38-27b", "dcgm-qwen36-35b-a3b", "otelcol-contrib"]`, `force_recreate: false`, and the full dashboard `env` map. Reject a plan that touches GLM, the filter, another model, proxy, nginx, or registrar. The collector configuration is inline and Compose may not hash it: require the action plan and running collector config to show the new Qwen3.8 r2/DCGM jobs. If the dry run leaves `otelcol-contrib` unchanged, first call `compose/down` on the current tag with `services: ["otelcol-contrib"]` (no dry run), then repeat this step's dry run and apply. This causes a brief collection gap; verify all scrape jobs return. Wait about 3–5 minutes for r2 readiness; inspect SGLang startup logs for the 0.85 KV allocation and 320 mamba slots, a real generation, GPU 2 VRAM, and the new scrape series.
3. Dry-run then apply `compose/up` on the Stage A tag with `services: ["proxy-qwen36-35b-a3b", "proxy-qwen38-27b"]`, `force_recreate: false`, and the full map. Confirm Qwen3.6 points only to r1 and Qwen3.8 sees healthy r1+r2. Immediately dry-run then apply `compose/up` with `services: ["nginx", "nginx-qwen38"]`, `force_recreate: true`, and the full map: nginx caches the proxy IPs through static `proxy_pass`. Proceed only if the dry run shows those two containers and no unrelated dependency recreation. Check both registrars still list the Qwen3.6 and Qwen3.8 endpoints in model-proxy; if either endpoint is absent **after one minute**, restart only its `model-proxy-registrar` or `qwen38-registrar`, with a scoped dry-run `compose/up` and full env map first.
4. Compare every container ID and `CreatedAt` with the baseline. Only the named services and explicitly needed registrar may change. Confirm Qwen3.6 and Qwen3.8 registry entries, real completions, and their synthetics. Soak under traffic; watch Qwen3.6 queue/TTFT and crashes, Qwen3.8 errors and GPU 2 VRAM, filter restarts and classify 5xx, and scrape continuity. Do not proceed to Stage B on a failed route, collector, or capacity check.

## Stage B: vacate GPU 0 (separate branch/tag)

With Stage A healthy and Stage B separately approved, down r1 on the **Stage A tag before any `compose/up` on the Stage B tag**. Compose Manager uses `--remove-orphans` even for scoped ups; once r1 is down, the Stage B up has no Qwen3.8 r1 orphan to remove.

1. On the **Stage A tag**, call `compose/down` with `services: ["model-sg-qwen38-27b-fp8-tp1-r1"]`; do not dry-run the down. Allow its five-minute graceful stop and wait for the container to exit. The old two-backend proxy marks r1 unhealthy within about 15 s, after which r2 serves alone. Check the Qwen3.8 endpoint, synthetic, a real completion through r2, and all container IDs/`CreatedAt`.
2. On the **Stage B tag**, dry-run then apply `compose/up` with `services: ["proxy-qwen38-27b", "otelcol-contrib"]`, `force_recreate: false`, and the full map. Include any DCGM service whose labels Stage B changes in this scoped up, and verify the intended label and collector configuration changes actually apply. Reject any plan that removes or recreates an unrelated service. Verify that the Qwen3.8 proxy's sole backend is r2 and that the collector has the Stage B scrape configuration. Immediately dry-run then apply `compose/up` with `services: ["nginx-qwen38"]`, `force_recreate: true`, and the full map, checking that no other container is in the action plan. Confirm the Qwen3.8 registry endpoint, synthetic, and a real completion.
3. Confirm GPU 0 free VRAM is approximately 138 GiB minus the privacy filter, and that no Qwen process uses GPU 0. Verify classify requests, filter process starts, Qwen3.6 queue/TTFT, Qwen3.8 completions, registry entries, and synthetics through a monitored soak.
4. **Separate approval required:** recreate only `model-privacy-filter` to pick up PR #223. Dry-run a scoped `compose/up` with `services: ["model-privacy-filter"]`, the full map, and `force_recreate: false`; review the planned recreation and preserve all other container identities. Verify a real representative classification, larger-batch behavior, GPU 0 VRAM, 5xx, process starts, and the privacy synthetic afterward.

If any action plan shows removal of live GLM or recreation of an unrelated service, stop before applying. A rollback must use a tag that defines the service being restored, a scoped dry-run up for each changed service, the original full env map, and a fresh registry/synthetic check; do not rely on orphan removal as a rollback mechanism.
