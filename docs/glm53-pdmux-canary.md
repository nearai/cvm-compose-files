# GLM-5.3 PD-Multiplexing + EAGLE (pdmux) canary: ONE base replica (gpu04 r4)

Status: **prepared, not deployed, image not yet published.** Merging changes no running service. gpu04 changes only when an operator deploys the merged tag to it, scoped to the one service below, through the already-running compose-manager. `PDMUX_IMAGE_DIGEST` in `scripts/prepare_glm53_pdmux_canary.py` is a **placeholder** until the image is published (next section); the canary file must not be deployed with it.

## What changes

| | gpu04 r4 (canary) | gpu04 r1-r3 (controls), gpu03 r1-r4 |
|---|---|---|
| image | **`glm53-hicache-w4afp8-v7-pdmuxe`** (see `PDMUX_IMAGE_DIGEST` in `scripts/prepare_glm53_pdmux_canary.py`) = v7 recipe + `pdmux-eagle.diff` | v7 `sha256:fa730e6e…` (gpu03 r4: v8 KDA canary, #354) |
| argv | v7 fleet argv **plus** `--enable-pdmux --sm-group-num 3 --pdmux-config-path /etc/glm53/pdmux-ov96-l4.yaml` | v7 fleet argv |
| unchanged | EAGLE 4/1/5, chunk 8192, `--prefill-decode-interval 2`, HiCache off, overlap scheduler off, `--max-queued-requests 32`, mem 0.86, `--max-running-requests 64`, mamba 380, every environment variable, GPUs 6-7 | same |
| `engine_image` / `config_variant` labels | new digest prefix / `...-v7-pdmuxe-ov96-l4` | unchanged |

PD-Multiplexing runs a prefill in layer slices on its own stream, in a green context capped at 96 SMs, beside decode, instead of in a pass that freezes every decoding request. The baked config (`/etc/glm53/pdmux-ov96-l4.yaml`):

```yaml
sm_group_num: 3
manual_divisions: [[96, 36, 1]]
split_forward_token_budget: 65536
max_split_forward_layers: 4
overlap_decode_full_sm: true
```

Prefill is capped at 96 SMs, decode keeps the full device, and at most 4 prefill layers launch per scheduler iteration. The patch is a port of upstream sglang PR #42411 (GLM PD-Multiplexing) and the single-layer MTP part of #42414, plus prototype fixes; it is inert without `--enable-pdmux`. Recipe: `docker/sglang-glm53-hicache-w4afp8-pdmuxe` (README section "PD-Multiplexing + EAGLE").

Files: `prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8-PdmuxCanary.yaml`, generated by `scripts/prepare_glm53_pdmux_canary.py` from the base fleet file. `scripts/test_glm53_pdmux_canary.py` asserts that only r4's image, command and telemetry labels differ, that the argv is the fleet argv plus exactly the three pdmux flags, and that it equals `pdmux-canary-argv.json`, the argv `test-cpu.sh` step 14 validates inside the image.

At 0.4 conv/s: freezes 11-12% -> 0.0%, TTFT p95 2.7x, total tok/s -14%, decode rate -17%. Quality: GSM8K-100 0.99, the same as v7.

- **Known costs on bare:** TTFT p95 2.7-4.5x, total throughput -14..-27%, 7% queue sheds at 1.0 conv/s with queue 8. Prod now runs queue 32 (#349), which should absorb part of the sheds at a TTFT price; the lab ran queue 8.
- Mechanism (inference, not profiled): pdmux redistributes GPU time instead of adding capacity. Prod prefill passes carry a ~0.65 s fixed cost with the GPU mostly idle (bare shows ~0.14 s), so the prod gain may be larger and the TTFT cost smaller than on bare. That is the hypothesis this canary tests.
- **Not yet measured under confidential computing (TDX + PPCIe).** Nothing of this has run in a TEE.

## Why gpu04 r4

gpu03 r4 carries the v8 zero-sync KDA canary (#354), so a pdmux canary there would mix two changes in one replica and take away its clean v7 control. On gpu04, r1-r3 are v7 and stay untouched: they are the same-host, same-traffic controls, and r4 differs from them only by pdmux. gpu04 r4 also keeps the two canaries on different hosts, so one host fault cannot take both.

## Rules

- **At most 2 base TP2 replicas down at once across gpu03/gpu04** (owner's limit). Check `/backends/list` and `docker/ps` on gpu03 and gpu04 first. Do not deploy while another base replica is recreating, and prefer to deploy when the gpu03 r4 v8 canary is up and stable, so this is the only replica down.
- **Never kill a running `compose/up`.** An interrupted apply leaves the replica created but not started; re-run the same scoped `up`, do not abort it. `compose/down` is never used.
- Tell the team (Henry) before the deploy, with the replica and time.
- The long tier is not part of this canary.

## Publish the image (human steps, before the canary file is usable)

The digest is unknown until the image is published, so the canary file ships with a zero placeholder.
1. Merge the image recipe PR (`docker/sglang-glm53-hicache-w4afp8-pdmuxe`, workflow variant `hicache-w4afp8-pdmuxe`) to `main`.
2. Run the workflow **Publish GLM-5.3 admission-reserve engine images** (`.github/workflows/publish-glm53-admission-reserve.yaml`) with `variant: hicache-w4afp8-pdmuxe`, an empty `tag` (default `glm53-hicache-w4afp8-v7-pdmuxe`) and `source_revision` = the exact 40-character merged commit on `main` that contains the recipe. It runs on the `infra` runners, from `main` only. It validates the pinned Dockerfile / PROVENANCE / SHA256SUMS hashes, builds, runs `test-cpu.sh` (steps 1-14) in the published image, scans, attests and signs.
3. Read the digest from the run summary line `immutable: docker.io/nearaidev/sglang@sha256:...` (#354 recorded it as a comment next to the constant: "published from main <sha>, #NNN; publish run <id>").
4. In the canary PR set `PDMUX_IMAGE_DIGEST` in `scripts/prepare_glm53_pdmux_canary.py` to that digest, note the run id in the comment above it, run `python3 scripts/prepare_glm53_pdmux_canary.py --write`, and confirm `python3 -m scripts.test_glm53_pdmux_canary` no longer skips `test_digest_is_published`.
5. Merge the canary PR. The deploy tag is the merged tag from that merge.

If `test-cpu.sh` step 14 fails in the publish run, the image is not signed and the canary must not proceed.

## Deploy (compose-manager, gpu04 only)

`POST /compose/up` with `tag` = the merged tag, `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8-PdmuxCanary.yaml`, `services: ["model-sg-glm53-w4afp8-tp2-r4"]`, the host's existing full `env` map, `force_recreate: false`. No KMS step and no env change.
1. `dry_run: true` first: the plan must recreate exactly that one service and nothing else.
2. Then `dry_run: false`. Poll `docker/ps` until r4 shows a NEW container `Up N minutes` on the new image. If it stays absent for over a minute, re-send the real scoped `up`; do not kill the running call.
3. Ready = `/health` 200, `/backends/list` shows r4 ready, and it serves traffic.

Cold start under CC is about 20 minutes. **Expected failure mode: boot failure.** Green contexts under CC are untested; if they fail, the engine exits during start-up and r4 never becomes ready. That is safe: the replica stays out of the pool, traffic stays on r1-r3 and the other host. Capture `docker logs` of r4, then roll back (below).

### Abort criteria

**Abort (roll back r4 only) on a crash, engine errors or not serving:** any engine exit or restart of r4, a Traceback, CUDA error, NCCL error or Xid on GPUs 6-7, `/health` not 200 or r4 not ready, or r4 not serving requests it was routed. **Latency gates are advisory** (the owner's rule): worse TTFT, more queue-full 503s, or lower total throughput are reported, not a reason to roll back by themselves. Report them at 2 h, the next peak and 24 h and let the owner decide.

## Risks

- **Green contexts under CC are untested.** Boot failure is the expected failure mode and it is safe (see above). A failure only after warm-up, under load, is the real risk: that is what the abort criteria cover.
- **Eager drafter.** Draft forwards run eager under pdmux (no draft CUDA graphs), the main suspect for the lower total throughput (decode rate -17% at 0.4 conv/s). Per-stream draft graphs are not built.
- **Prototype status.** A port of upstream PRs with local fixes; n=1 per lab cell; one crash was found and fixed in the first GPU run (fix 1). The extra decode fence (`SGLANG_PDMUX_EAGLE_DECODE_FENCE`, default 1) measured no effect, so leave it as is.
- **Capacity.** The lab shows a prefill-bound 4.5x TTFT and 7% sheds at 1.0 conv/s; r4 may shed more than its peers at peak. Blast radius is 1 of 8 base replicas (12.5% of base capacity); the proxy only routes to ready replicas.
- Not covered by the port or the lab: DP-attention (skipped in the port) and HiCache with pdmux (a pdmux HiCache test exists but HiCache is off in the fleet argv and stays off here).

## Rollback

`compose/up` of `model-sg-glm53-w4afp8-tp2-r4` with the same tag and `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8.yaml` (the v7 fleet file), `dry_run` first. Same one-replica rule and the same "never kill a running `up`".
