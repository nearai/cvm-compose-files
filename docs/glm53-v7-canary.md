## How a host is pointed at a file (compose-manager)

There is no per-host file setting in this repo. The README's deploy command shows the whole contract: each `POST http://<host>:8080/compose/up` call carries `tag` (a `v0.0.N` tag, deployable once its commit passes `MIN_TAG_AGE_HOURS`), `file` (repo-relative path **with** the `prod/` prefix), `services` (list), `env` (the host's full env map from gpu-manager), `force_recreate` and `dry_run`. compose-manager runs `docker compose up -d --remove-orphans` for that file in its project (`work` on serving hosts; an optional `"project"` field exists, see `docs/migration-gpu-preflight.md`). So "gpu03 runs file X" only means that the last deploy named X; the new file is selected by naming it. The env map is the host's existing one and is not edited.

## Deploy (merge, tag, then compose-manager on each canary host)

No registration step beyond the tag and no env-map change: deploys go only through the already-running compose-manager with the tag.

1. Merge, wait for the tag to clear the age gate, note the tag `T`.
2. **Pre-checks on the canary host** (gpu03 for base, gpu02 for long): `docker/ps` and `/backends/list` healthy; all controls up on v6 with the expected argv (base: `max_running_requests=48`, mem 0.86; long: 12/4); the host's env map dumped as the rollback reference. Base: look for extra prefill/decode (pf/dc) services that have recently shown in gpu03's metrics and make sure none holds GPUs 6,7 or enough host RAM for the 4 x 325 GiB HiCache tiers. Long: gpu02 runs four TP2 replicas (r1a, r1b, r2a, r2b) at 12/4 per the capacity doc; a TP4 replica or a 24/8 replica is not a matched control. Base fleet rule: start only when every other base replica is up (see rules).
3. `compose/up` with `dry_run: true`, `tag: T`, `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8-V7Canary.yaml` (gpu03) or `prod/GLM-5.3-Flash-SGL-TP4-W4AFP8-LongContext-V7Canary.yaml` (gpu02), `"services": ["model-sg-glm53-w4afp8-tp2-r4"]` (gpu03) or `"services": ["model-sg-glm53-w4afp8-tp2-r2a"]` (gpu02), `force_recreate: false`, the host's full env map. **The plan must show exactly one recreate (the canary) and nothing else** (no `model-downloader`, no proxy, no nginx, no other GLM replica, no `--remove-orphans` removals). Apply the same call with `dry_run: false`.
4. Wait for ready (about 22 minutes cold start under CC) and run "Verify".
5. `compose/up` with `"services": ["otelcol-contrib"]`, `force_recreate: true`, `dry_run` first (plan: collector only). Last on purpose, so the canary's labels change when it is already v7. Verify the canary's `config_variant` ends `-v7` / `-v7-mr16q4` and the controls' are unchanged.
6. Confirm the controls, proxy, nginx and registrar were never recreated (container IDs and uptime unchanged).

**Risks of switching a host's file, and why the scoped call contains them**
- *Project and container names.* Both files define the same project and the same container names, so the scoped `up` recreates the canary container in place and never starts a second copy. The `deployment`, `container_name` and instance labels are unchanged on purpose.
- *Other services.* The canary file's other services are textually identical to the source file's, so compose sees no config change for them. A call **without** a `services` list would still only recreate what changed, but never rely on that: an empty list is forbidden here; only `["<canary service>"]` and `["otelcol-contrib"]`.
- *`depends_on`.* The canary depends on `model-downloader` (one-shot, completed). The dry-run must not show it recreated; if compose-manager has no no-deps option and the plan includes it, stop.
- *Orphans.* `--remove-orphans` removes any running service the applied file does not define. The canary file defines every service of the source file, so none is removed; still read the plan.
- *The host now "runs" the canary file.* A later routine deploy of the host's normal file with the canary service in its `services` list (or unscoped) recreates the canary on v6: that is the rollback, and an accident to avoid mid-bake. Tell whoever deploys to gpu03/gpu02 to pause normal deploys for the bake, and always scope them.

## Rules (user rules)

- **Long context: one replica at a time, and wait until it is back serving and baked.** Only r2a is touched; r2b, r1a, r1b, gpu23 and gpu13 are not recreated or re-tagged until r2a is back serving (`/backends/list` healthy, a long-domain completion plus a cache-hit follow-up) and its bake has been read.
- **Base: never more than 2 base replicas down fleet-wide.** The canary takes 1 down for about 22 minutes. Before each canary or rollback recreate, check `docker/ps` and `/backends/list` on gpu03 and gpu04: start only when every other base replica is up, so the canary plus one unplanned failure stay within 2.
- **`compose/down` takes effect immediately and cannot be recalled; it ignores `dry_run`.** This runbook never needs one (`compose/up` of the scoped service recreates it). If a `compose/down` is ever sent, scope it to one service, do not dry-run it, and **verify in the host's compose-manager action log** that the logged services list is exactly that service; cross-check with `docker/ps`.

## Self-profile (canary only)

`NEAR_SELF_PROFILE=1` runs the #343 hook once per engine start on TP rank 0, `NEAR_SELF_PROFILE_AFTER_S=900` seconds (about 15 minutes of warm traffic) after start, for `NEAR_SELF_PROFILE_STEPS=50` steps. Expect a one-time stall of a few seconds, up to about 20 s, once per start, about 15 minutes after start (not a stall abort: once, TP rank 0, on the canary only). Read the result in Loki: `{host="gpu03", container_name="model-sg-glm53-w4afp8-tp2-r4"} |= "NEAR_PROFILE"` (long: `{host="gpu02", container_name="model-sg-glm53-w4afp8-tp2-r2a"} |= "NEAR_PROFILE"`). If CUPTI is unavailable under CC the hook retries CPU-only (`retrying cpu-only`); to force it add `NEAR_SELF_PROFILE_ACTIVITIES=cpu` to the canary service's environment and regenerate. An error prints one `NEAR_PROFILE error ...` line and disables the hook; that is not an abort. The bake read must exclude the profiling minute (15 minutes after ready, plus one minute either side), symmetrically for all replicas.

## Evidence

All from nearai/tee-bench (lab, gpu32, bare metal, CC off unless noted):

- **exp 26, `evidence/gpu32-fp8-kv`**: FP8 KV on stock v6 fails on every DSA backend; `--max-running-requests 64` with bf16 alone gave +8-13% tok/s.
- **exp 27, `evidence/gpu32-fp8-kv-fix`**: the route A' patch (the one in v7) works: KV pool x1.467, quality equal (GSM8K 0.99, passkey 3/3).
- **exp 29, `evidence/gpu32-fp8-vram-matrix`** (README): base FP8 at 64 running / 380 mamba slots: mean 1043 tok/s against 886 for bf16 prod in the same session (+18%), +11-17% against exp 26's best bf16 arm. Long FP8 16/6 against bf16 12/4: +10-11% tok/s, +12-13% served, TTFT p95 +18% (L2 0.06) and +21% (L2 0.09), 1M-token prefill OK (88 against 94 s). **16/4, the setting this canary runs, was not measured**; it follows the pre-agreed rule "16/4 if the TTFT tail worsens".
- **`evidence/long-tp2-wedge-rca`** (README, `WEDGE-RUNBOOK.md`): the long-tier preprocessor wedge, 7 events since 2026-09-24. Pool plus deadline fix: 962 against 117 tok/s under injected stalls, TTFT p95 1.6 against 119 s, no regression without stalls (-1.5% / -2.1%).
- **Production cache data** (Grafana, 24 h, 2026-10-07): long tier 84% cached against an 84.1% infinite-cache ceiling; base 60% against 66%. FP8's larger KV pool therefore has little prefix-cache headroom to win on the long tier; its gain there is slots and decode speed.

## The bake (3-4 hours, and it must include a busy period)

**What this bake is.** A safety and smoke gate. In 2-3 read hours it can falsify (crash, Xid, OOM, stall, a clear latency or error regression, a tool-call collapse); it cannot establish a throughput gain, attribute anything to one of the five changes, or say anything about capacity. An efficacy read needs about 12-24 h on the same canary under the rule below.

**Clock.** Starts at the later of "canary ready" and "collector recreated", plus 60 minutes of warm-up and until the canary's HiCache and prefix hit rate are within 10 points of the controls for 30 consecutive minutes (cold caches, no conversation-affinity pins); the controls are excluded for the same period. Schedule it so the read contains at least one hour of the three busiest hours of the same weekday over the last 7 days (fix the slots from Grafana beforehand).

**Compare the canary with its same-host controls** on: requests served, prompt tok/s, generation tok/s, cached-token share, TTFT p95, ITL p95, 422 and preprocess-timeout counts, restarts, Xid, and the self-profile output at 15 minutes. Read tok/s at matched `num_running_reqs` bins crossed with context tokens, never as a ratio of sampled gauges; p95 from summed histogram buckets over the window. Confounds to report: the proxy is least-connections with affinity, so a faster replica (and a larger cap) attracts more concurrent requests and the canary receives only new conversations after its restart (shorter, younger contexts); report request share, mean prompt and output tokens and conversation age per arm, and call tok/s and ITL mix-confounded if the canary's mean prompt differs by more than 10%. The bins the new caps open (base 49-64, long 13-16) have no control and are descriptive. gpu04's r4 (base) and gpu23's r2a (long) give the same canary-to-controls ratio on the untouched host: a difference-in-differences reference. Long r2a is chosen because both observed preprocessor wedges hit r2a slots (likely routing-pinned traffic): the preprocessing fix is exercised under the traffic that triggered the stalls, which can also turn pathological requests into fast 422s and make the canary serve cheaper requests; report request outcomes and restrict the matched comparison to requests the controls also accepted. If that confounds the read, redeploy the canary on r2b (change `service` in the generator and regenerate).

**Efficacy rule if extended** (fixed before the bake): the log ratio canary/controls, stratified by cell, bootstrapped over 30-minute blocks; read once at a stop fixed beforehand; "consistent with the target" only if the interval contains the claimed gain and its lower bound is above +10%. Do not read the 30-minute safety checks as efficacy evidence.

## Abort criteria (pre-registered; any one means roll back)

Safety looks every 30 minutes by a named person; one-sided, trailing windows.

1. Any exit or restart of the canary container, any Xid on its GPUs, any OOM, CUDA or NCCL error, watchdog or scheduler-stall message.
2. Free GPU memory under 2 GiB for 5 minutes.
3. Preprocess-pool timeout storm or worker death more than 3 times in 10 minutes, or image or tool-schema requests failing where the controls' do not.
4. No tokens for 30 seconds with a decode-phase request while the controls generate (a prefill-only interval is excluded; the one-time profiling stall is not this).
5. **TTFT p95 or ITL p95 more than 20% worse than the controls** (one-sided 90% lower bound above +20% over a trailing 90 minutes with at least 12 blocks and 300 requests, or point estimate above +50% over 30 minutes). Known risk: the long tier's TTFT p95 tail was +18% / +21% in the lab even at 16/6, so expect this to bind first on long; the first remedy (16/4) is already applied, the next would be 12/4 caps on FP8. Long TTFT p95 cannot be bounded at about 1,500 requests: it is reported, and a judgment abort only at a point estimate above +50% over 90 minutes.
6. 5xx other than queue-full 503, or aborts, when the 95% lower bound of the rate difference exceeds 1 point over 90 minutes (long: 2).
7. Queue-full 503 above the controls by more than 3 points over 30 minutes while below the cap.
8. Gross quality-proxy failure: tool-call parse failures or empty outputs above the controls by more than 2 points over 60 minutes.

Not an abort by itself: the canary's request share rising, EAGLE accept length moving, a transient TTFT spike inside the warm-up. A judgment abort rolls back the whole bundle; piece rollbacks restart the warm-up.

## Rollback

Rollback = redeploy the canary service from the original file. `compose/up`, `dry_run` first, `tag: T` (or the previous tag), `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8.yaml` (gpu03) or `prod/GLM-5.3-Flash-SGL-TP4-W4AFP8-LongContext.yaml` (gpu02), `"services": ["<canary service>"]`: the plan recreates only the canary, back on the v6 image with the original argv. Then `["otelcol-contrib"]` with `force_recreate: true` so the labels follow. Verify the startup log shows `kv_cache_dtype=bfloat16`, `disable_overlap_schedule=False` and `docker inspect` shows the v6 digest. For a single feature without a restart of the whole bundle there is no env-map lever any more: regenerate the canary file without that line and redeploy the canary service (each recreate is a 22 minute cold start and counts against the rules above). The controls, proxy, nginx and registrar are never touched.

## What this canary cannot show

Overlap-off alone, FP8 KV quality (the lab parity is exp 27; this bake reads only quality proxies), a capacity gain at SLO, restart or cold-cache effects separate from the bundle, anything in the bins the controls cannot reach, or anything beyond one replica on one host.
