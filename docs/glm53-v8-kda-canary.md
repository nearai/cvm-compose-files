# GLM-5.3 Flash v8 zero-sync KDA canary: ONE base replica (gpu03 r4)

Status: **prepared, not deployed.** Merging changes no running service. gpu03 changes only when an operator deploys the merged tag to it, scoped to the one service below, through the already-running compose-manager.

## What changes

| | gpu03 r4 (canary) | gpu03 r1-r3 (controls), gpu04 r1-r4 |
|---|---|---|
| image | **v8** `glm53-hicache-w4afp8-v8` (see `V8_IMAGE_DIGEST` in `scripts/prepare_glm53_v8_kda_canary.py`) | v7 `sha256:fa730e6e…` |
| argv / environment / GPUs | v7 fleet, unchanged | v7 fleet |
| `engine_image` / `config_variant` labels | v8 digest prefix / `...-v7-kda` | unchanged |

v8 = v7 + `kda-zero-sync.diff` (#352) and nothing else: KDA prefill takes its token count from host metadata instead of a GPU→CPU read in each of the 34 KDA layers per prefill chunk. Under TDX+PPCIe each of those reads drains the GPU queue. tee-bench exp 37 (gpu31 TEE lab): prefill step −4..−10%, ITL p95 −8..−10%, TTFT p95 −5..−15%; total tok/s inside the control spread, so **capacity is not established** and the decision is on latency.

File: `prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8-V8KdaCanary.yaml`, generated by `scripts/prepare_glm53_v8_kda_canary.py` from the base fleet file; `scripts/test_glm53_v8_kda_canary.py` asserts that only r4's image and its two telemetry labels differ.

## Rules

- **One replica out of the pool, fleet-wide.** No other base or long replica may be down or recreating when r4 is recreated. Check `/backends/list` and `docker/ps` on gpu03 and gpu04 first; all eight base replicas must be up.
- **Tell the team (Henry) before the deploy**, with the replica and time.
- The long tier is NOT part of this canary. A long-tier step comes only after the base read, and again one replica.
- `compose/down` is never used.

## Deploy (compose-manager, gpu03 only)

`POST /compose/up` with `tag` = the merged tag, `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8-V8KdaCanary.yaml`, `services: ["model-sg-glm53-w4afp8-tp2-r4"]`, the host's existing full `env` map, `force_recreate: false`.
1. `dry_run: true` first: the plan must recreate exactly that one service and nothing else.
2. Then `dry_run: false`. Poll `docker/ps` until r4 shows a NEW container `Up N minutes` on the v8 image; if it stays absent for over a minute, re-send the real `up` (a recreate can be left in `Created`).
3. Ready = `/health` 200, `/backends/list` shows r4 ready, and it serves traffic.

Cold start under CC is about 20 minutes.

## Bake and reads

Same 5-minute bake checklist as `docs/glm53-v7-fleet-rollout.md` (ready and routed, dashboard, clean logs, serves traffic, latency vs peers). Controls are gpu03 r1-r3 over the same window.

Reads at 2 h, at the next peak and at 24 h, r4 vs r1-r3:
- TTFT p50 / p95 / p99 (`sglang_time_to_first_token_seconds`), ITL p50 / p95 (`sglang_inter_token_latency_seconds`) at matched running;
- prefill and decode step time from `Prefill batch` / `Decode batch` log windows (tee-bench exp 34 method);
- queue depth, queue-full rejections, 5xx;
- served prompt and generation tok/s.

**Success:** TTFT p95 and ITL p95 each at least 5% better than r1-r3, with no served tok/s regression.
**Abort (roll back r4 only):** TTFT p95 more than 10% worse than r1-r3, any Xid / CUDA error / `KDA host token count` error / engine exit, retraction spike, or 5xx above the controls.

`compose/up` of `model-sg-glm53-w4afp8-tp2-r4` with the same tag and `file: prod/GLM-5.3-Flash-SGL-TP2x4-W4AFP8.yaml` (the v7 fleet file), `dry_run` first. Same one-replica rule.
